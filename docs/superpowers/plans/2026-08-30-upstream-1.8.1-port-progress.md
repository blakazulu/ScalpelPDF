## Execution model

Compiled C# cannot be edited by several agents in one working tree (each agent's build sees
the others' half-finished edits). Parallel waves therefore run in **detached git worktrees**
(`git worktree add --detach`, no branch created) under `C:\Code\Personal\_wt\`, each agent
owning a disjoint file set; results come back as `git diff` patches applied to the main tree
with `git apply --3way`. Locale keys: agents add new keys to `Strings/en-US.xaml` only, inside
a `<!-- port: <wave> -->` block; the other 8 locale files are filled in one pass per wave.
Agents never edit `Services/Changelog.cs` or this tracker; they report entries and I add them.

### A real crash found while testing upstream's #141 claim
Verifying whether Docnet's annotation flag is safe surfaced a **live AccessViolationException**
in `FPDFDOC_ExitFormFillEnvironment` during Docnet's document teardown. It is NOT caused by the
annotation flag and is not new: PDFium is single-threaded with global state, and Scalpel rendered
concurrently (sidebar thumbnails at `SemaphoreSlim(2,2)` plus background continuous/grid tile
tasks plus the UI thread's primary render). On .NET Framework an AccessViolation is not catchable
without `HandleProcessCorruptedStateExceptions`, which `App.xaml.cs` deliberately omits - so it
kills the process with no crash dialog and nothing in the log.

`Services/PdfiumGate.cs` (gap-A item **A7**, previously owed) now serializes every Docnet document
reader for its whole lifetime - open, render AND dispose, since the teardown is where it faults -
at all 9 render sites plus `DocnetPageRasterizer`, which holds the gate for its object lifetime.

**Residual, deliberately left and documented:** PDFium's form-fill teardown is also thread-affine,
so a document created on one thread and disposed on another can fault even when properly
serialized. Fixing that means marshalling all rendering onto one dedicated PDFium thread, which
cannot be dropped in as-is: the streaming render loops call `Dispatcher.Invoke` from inside the
reader scope and would deadlock against a UI thread waiting on the same gate. Three tests in
`PdfiumGateTests` / `AnnotationRenderTests` carry the reproducer and are `Skip`ped with that
reason rather than left flaky.

modifier comparison that Shift broke), `PinchZoomMath` (touch pinch did nothing),
`DeferredActionGate` (stale zoom scroll-restores), `PageQualityConverter` + new export-as-images,
`PdfPageDifference` + new compare tool, `MeasurementCalculator` + new measure tool,
`PerspectiveWarp` + new straighten tool, `FormOcrPolicy` + new fill-by-OCR tool,
`CombFieldLayout` (comb fields, in the overlay *and* the saved appearance stream),
`TextRunService` (copying from a two-column PDF interleaved the columns), and
`TextEntryPlaceholder` (clicking a printed dotted blank now drops the text box onto the line).

**A4 conformance: three of the five items were never broken.** Measured by reading the bytes of a
real save rather than trusting the inherited list. `/ModDate` is not written at all, booleans are
already lowercase, and `/Length` is already a direct integer. The two real ones -
PdfSharpCore stamping its own name into `/Producer`, and attaching a DeviceRGB transparency
`/Group` to every page it draws on - are both fixed **without vendoring**, which the tracker had
assumed was required. Both are corrected in the finished bytes (Save writes them after any
object-model fix-up), and both rewrites are length-preserving so no cross-reference offset moves;
tests assert the file length is unchanged and that it still reopens. The three non-issues are
regression-guarded so a future PdfSharpCore cannot quietly reintroduce them.

**PDFium: fixed, and the recorded cause was wrong.** The note said the residual was thread
affinity and that the fix was blocked on the render loops calling `Dispatcher.Invoke`. Marshalling
everything onto one dedicated thread did *not* fix it, so four hypotheses were tested and refuted
in turn: cross-thread access, reader churn (40 open/dispose cycles pass in isolation), malformed
input (fault persists with the hostile corpus excluded), and GC finalization of abandoned readers.
What actually resolved it was disabling xUnit's assembly-level parallelization: PDFium is a
process-global singleton, so the test host interleaving whole classes is unsound no matter how
well the app serializes its own calls. All three previously-skipped reproducers now pass across
six consecutive full runs, and **the suite has zero skips**.

The dedicated-thread work was kept because it is independently correct - it matches PDFium's
documented single-thread contract, it fixed a real reader leak in `DocnetPageRasterizer`'s
constructor (a throw after the reader opened left it to the GC finalizer), and it makes PDFium's
one-time init deterministic. Only the native calls are marshalled, never whole loops: running a
loop on the PDFium thread would block it on `Dispatcher.Invoke` while the UI thread waited on
PDFium, which is the deadlock the old note predicted.

**Also fixed:** cropping a page rotated 180 degrees kept the mirrored half. `MainWindow.Crop.cs`
and `MainWindow.Forms.cs` each hand-derived the canvas/PDF transform and disagreed at exactly that
one case; at 180 the rotation flip and the y-up/y-down flip cancel, so y must pass through
unchanged. Forms.cs was right. Because Crop's forward and inverse copies were wrong in the *same*
direction the round trip agreed with itself, so the overlay looked correct while the saved
`/CropBox` was wrong. Now one derivation in `Services/PageSpaceMap.cs`, used by both.

### Closed 2026-08-31 (second pass): E2E Tools coverage and comment editing

**Tools menu is now in the E2E catalog** - 21 menu items plus the button that opens them, taking
the singles suite from 39 to 61 checks with full coverage. Three things had to be built for it:

- Every Tools/File `MenuItem` gained an `x:Name` (derived from its Click handler, so the id is
  obvious and stable). `MenuItem.ClickEvent` was already hooked by the app's global click logger,
  so no app-side logging change was needed.
- `Surface.ToolsMenu` reopens the ContextMenu before each item, because clicking one closes it.
- `AppDriver.Find` now falls back to `FindInPopups`. A WPF ContextMenu renders in its own popup
  HWND, so its items were never descendants of the main window and a main-window-only search could
  not see them at all.

Every catalogued Tools item opens a modal that `ActionRunner.DismissModals` closes immediately
after, which cancels the operation - so the scan exercises each handler's real entry path without
altering the document. `DismissModals` was strengthened to escalate (Close, then the dialog's own
Cancel button, then Escape) because a native Open/Save dialog routinely survives `Close()`.

**A latent harness bug surfaced while doing it, and was the real cause of the mess.**
`ResolveMainWindow` picked "the first top-level window that is not a Popup". A native file dialog
has ClassName `#32770`, which passes that test - so while any file dialog was open the driver could
cache the *dialog* as the main window. Every `Find()` then searched the dialog; the coverage
cross-check reported the dialog's own chrome (UpButton, DropDown, GUID-named parts) as
un-exercised Scalpel controls; and worst, `GetMainWindowHandle` derives from `MainWindow`, so
`DismissModals` would have protected the dialog and closed the real window. It now keys off the
process's own main-window handle, pinned at launch before any dialog can exist. This was always
reachable through Open/Save - the Tools work only made it show up.

**Comments are editable.** `PdfComments` gained `UpdateContents`, `UpdateAuthor` and `Delete`, and
`PdfComment` now carries the page and annotation index needed to find the annotation again. Two
details matter and are covered by tests: editing drops the annotation's cached `/AP`, because a
viewer that finds a stale appearance stream draws the OLD words (the edit would appear to work in
Scalpel and nowhere else); and deletions are applied highest-index-first, because removing one
annotation shifts the index of every later one on that page. A stale locator is refused rather
than applied blindly, so a comment held across an unrelated edit cannot rewrite the wrong
annotation. `CommentsWindow` is the editor; nothing is written until Save, the edits land in the
open document behind a `PushDocUndo`, and the user still saves the file normally.
